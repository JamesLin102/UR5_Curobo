# 規劃書：給 RL 用的第二個情境 —— 在圓柱之間夾取立方體

狀態：**規劃中，尚未實作**（2026-09-24）。只在 Isaac Lab backend 上做；Isaac Sim backend 維持凍結，不跟進。

## 1. 目標與已定案的決定

一個比 `pick_place` 更單純、適合 RL 的情境：

- **場景**：一張桌子（cuRobo 知道的障礙物），桌上一個立方體，周圍散佈幾根圓柱。
- **任務**：把立方體夾起來、抬離桌面，不放置。
- **分工**：policy 決定「從哪裡、用什麼角度夾」；cuRobo 負責所有移動與避障，和現在的 `PickPlaceEnv` 一樣。
- **最終目標是實機。**

已定案（2026-09-24）：

| 決定 | 內容 |
|---|---|
| 訓練時 | **cuRobo 直接知道圓柱的位置**（特權 planner），不開 mapper、不 render 相機 |
| 評估時 | **開 mapper**，圓柱只能靠相機建圖發現 |
| 立方體位姿 | **從感知來**，不用模擬器真值 |
| 原則 | **actor 的每一個輸入，實機上都拿得到。** 模擬器真值只能用在 reward、終止判定和 critic |
| 圓柱 | **固定尺寸：半徑 35 mm、高 0.30 m**，只隨機數量與位置 |
| 相機 | **只有腕部 D435i**，和實機一樣；模擬的這個情境也拿掉 overhead |
| 掃描 | **每個 episode 一開始先掃描**：建圖與感知都從掃描來 |
| 算力 | **盡量用 GPU**：目標是 GPU PhysX + 批次規劃，規模 128 環境以上（§9） |
| 程式架構 | `scripts/` 下只放共用的；**兩個範例各自一個資料夾**（§8） |

`pick_place` 情境不受影響，仍然是 wrist + overhead。

### 為什麼這個任務值得用 RL

立方體加上準確的位姿，手寫規則（對準中心、夾爪對齊一組面）在空曠桌面上幾乎百分之百成功。RL 的價值來自**規則會失敗的地方**：

1. **圓柱比手腕還高**：預抓取點的工具高度約 0.17 m（§2），圓柱頂在 0.30 m，整個手腕（FT 300、Wrist Camera、D435i 支架）都要伸進圓柱之間。
2. **可達性**：yaw 和 yaw+180° 對手臂是不同的姿態（腕部相機在一側），靠近工作空間邊緣時只有其中一個規劃得出來。
3. **感知誤差與遮擋**：立方體位姿有誤差，高圓柱會擋住立方體（§4）。policy 要學會在有誤差的估計下留餘量。

第一個里程碑是手寫的 oracle，量它在各難度與各感知誤差下的成功率；RL 的目標是贏過它。

## 2. 場景設計：`scripts/grasp/scene.py`

| 物件 | 類別 | 規格 |
|---|---|---|
| 桌子 | `obstacles` | 沿用 `pick_place` 的 2.0 × 2.0 × 0.10 m，桌面 z = 0 |
| 立方體 | `payload` | 45 mm、0.15 kg，和現在的 block 一樣；顏色和桌面強對比（例如亮黃），和實物一致 |
| 圓柱 | `unmapped`（形狀新增） | **固定半徑 35 mm、高 0.30 m**，0–4 根，kinematic 碰撞體 |
| 相機 | `cameras` | **只有 `wrist`**；深度 + RGB，RGB 對齊到深度 |
| 地圖 | `mapper` | 評估時用，格點沿用 `pick_place`；`floor_z` 要重新檢查（§11） |

### 夾取高度

立方體直接放在桌上。沿用 `pick_place` 的公式、改以桌面為基準：

```
GRASP_Z = 桌面 0 + pad_half 0.019 + pad_close_drop 0.0135 + PAD_CLEARANCE 0.012 ≈ 0.045 m
預抓取點 = GRASP_Z + descend_m 0.125 ≈ 0.17 m        （圓柱頂 0.30 m 之下）
```

`PAD_CLEARANCE` 在桌面上要重新量（手指不碰桌、重疊 ≥ 25 mm）。

**下降段整段都在圓柱之間，而且是開環的。** 在 server 端加「直線下降是否碰撞」的檢查（用 planner 同一個碰撞世界），不通過就當成 IK 失敗，不執行。實機上這是安全必需的。評估模式下要排除估計立方體周圍的體素，否則手指一定會「碰到」立方體本身。

### 每個 episode 隨機化

- **立方體**：位置在可達區域內（初值 x 0.30–0.60、y −0.35–0.35），yaw 在 [−π/4, π/4)（90° 對稱）。
- **圓柱**：數量 0–4，位置拒絕取樣：
  - 圓柱與圓柱、圓柱與立方體之間表面距離 ≥ 15 mm。
  - **至少存在一個可行的夾取**：先用夾爪加手腕的俯視外框粗篩，再用 server 的 collision-aware IK 在預抓取點與夾取點確認。
  - 立方體在**至少一個掃描視角**裡可見比例夠高（§4），否則重抽。
- **課程**：圓柱數量與「離立方體最近的距離」由寬鬆到擁擠。

**實機對應**：35 mm 半徑、30 cm 高接近 70 mm 外徑的 PVC 管或紙筒；立方體用 45 mm 木塊，漆成和模擬一樣的顏色。

## 3. 掃描與觀察姿態

只有腕部相機，所以**手臂要移動才看得到東西**。每個 episode：

```
reset → 掃描（建圖 + 感知）→ 回 HOME → 嘗試 1 → 回 HOME 感知 → 嘗試 2 → …
```

### HOME = 主觀察姿態

把 HOME 設成**腕部相機在工作區上方往下看**的姿態，初值：相機約在 (0.45, 0, 0.65)，光軸朝下。

- 這個高度下 640×480、水平 69° 的相機，桌面視野約 0.90 × 0.67 m，涵蓋整個工作區（0.30 × 0.70 m）。
- 一個像素約 1.4 mm，**立方體頂面約 32 個像素寬**。比原本 1.2 m 高的 overhead（約 12 個像素）好很多。
- 每次嘗試前手臂都在 HOME，所以「回 HOME 重新感知」不用額外動作。
- 要用 IK 確認 UR5 帶著整串腕部配件到得了這個姿態，並確認手臂本身不擋住視野（M2）。

### 掃描姿態

HOME 加上 2–4 個斜視姿態（從左、右、前方往工作區看）。斜視的目的：

1. **看到圓柱的側面**：只從正上方看，柱身在地圖裡是未觀測。
2. **看到被圓柱擋住的區域**：從不同方向看，陰影落在不同地方（§4）。
3. 給感知模組多個視角融合。

### 掃描姿態必須對任何圓柱配置都安全

評估模式下，掃描時地圖還是空的，planner 不知道圓柱在哪。所以掃描姿態、以及姿態之間的移動，**對任何一種圓柱配置都必須不碰撞**：

- 把「工作區 × 高度 0–0.32 m」整塊當成虛擬障礙物，離線驗證每個掃描姿態與姿態之間的關節內插，整隻手臂（碰撞球）都在它之外。
- 驗證結果寫進 `grasp/scene.py` 的註解，和 `pick_place` 記錄 slab 淨空的方式一樣。
- **D435 的最近深度約 0.28 m**（實機），相機離圓柱頂要保持 0.3 m 以上，這也限制了掃描姿態的高度。模擬的 `near` 從 0.15 改成 0.28，和實機一致。

### 訓練模式不掃描

訓練模式不 render，掃描看不到任何東西，所以**手臂直接放到 HOME、不跑掃描動作**，節省模擬時間。掃描的效果由誤差模型代表（§4 的多視角可見度）。評估模式與實機一定掃描。

## 4. 感知：實機拿得到的資訊

### 感知模組：`scripts/grasp/perception.py`

不 import Isaac 或 cuRobo（實機上兩者都沒有）；可以用 numpy 與 OpenCV。實機上同一份程式直接用。

**輸入**：掃描中每個視角的深度圖 + 對齊的 RGB、相機內參、該幀的相機位姿（**由正向運動學給出**：關節角 + eye-in-hand 標定）、桌面平面。

**輸出**（固定格式，和訓練時合成的一模一樣）：

```
cube:      (x, y, yaw) + 可見比例 + 擬合殘差
cylinders: 最多 4 根，每根 (x, y)
```

**流程**（每個視角各做一次，再融合）：

1. **取像**：每個視角停下來拍 5–10 幀平均（實機加 librealsense 的 spatial、temporal filter）。場景是靜止的，不怕延遲。
2. **分割，用深度**：深度 → 點雲 → 轉到基座座標系 → 只留桌面以上（z > 10 mm）→ 俯視高度圖 → 連通區域分群 → **依頂面高度分類**：約 0.30 m 是圓柱，約 0.045 m 是立方體。
3. **圓柱**：對頂面擬合已知半徑 35 mm 的圓，只解圓心。
4. **立方體，邊界用 RGB**：深度的邊緣有飛點，不能定邊界。在立方體那一群的範圍裡用顏色門檻取頂面遮罩，投影到 z = 0.045 m 的平面，擬合**已知邊長 45 mm 的正方形**（`minAreaRect` 取初值，邊界點到四邊的最小平方微調）→ 中心與 yaw（mod 90°）。
5. **可信度**：可見比例 = 看到的頂面像素 ÷ 由已知尺寸與相機幾何算出的預期像素；擬合殘差 = 邊界點離正方形的平均距離。
6. **多視角融合**：以可見比例與殘差加權；圓柱依位置配對後平均。

**標定**（實機，只做一次）：內參用 RealSense 出廠值；腕部相機外參用 ChArUco 板做 eye-in-hand 標定，確認 URDF 的 `camera_link` 誤差；桌面平面用 RANSAC 擬合。

### 遮擋

腕部相機在 HOME 的高度（0.65 m）比原本的 overhead（1.2 m）低，**陰影反而更長**。圓柱在離相機正下方 d 處，立方體頂面高度的陰影長度約

```
(0.30 − 0.045) × d / (0.65 − 0.30) ≈ 0.73 d        d = 0.2 m 時約 15 cm
```

這就是斜視掃描姿態存在的理由：從不同方向看，陰影落在不同地方。取樣時用每個掃描視角的相機位姿做幾何可見度計算，**立方體在最好的那個視角裡**可見比例低於門檻（初值 60%）就重抽；實機上感知模組回報可見比例，太低就不夾。

### 精度不夠時：近拍

如果 M4 量到 HOME 的 yaw 精度仍不夠，在夾取前多一個近拍：手臂移到估計立方體上方約 0.35 m（相機到立方體頂面 ≥ 0.3 m，D435 的最近距離），立方體約 60–70 個像素寬。這個姿態在圓柱頂之上，評估模式下地圖已經有圓柱，planner 可以規劃過去。

### 訓練時的誤差模型

每個 episode 從真值合成感知輸出，加上：

| 誤差 | 初值 | 校正來源 |
|---|---|---|
| 立方體位置 | σ = 2 mm，隨可見比例放大 | 評估模式下感知模組 vs 真值 |
| 立方體 yaw | σ = 2°，隨可見比例放大 | 同上 |
| 圓柱圓心 | σ = 3 mm | 同上 |
| 漏看圓柱 | 每根 2%，被擋住的更高 | 同上 |
| 誤判 | 小機率多一根假圓柱 | 同上 |

可見比例用掃描姿態的相機位姿做幾何計算（取最好的視角），不需要 render。先用初值訓練，M4 在評估模式下量實際誤差回頭修正；**實機上用 ArUco 取真值**再量一次（見下）。範圍要比量到的寬一點（domain randomization）。

### 實機的感知誤差怎麼量

- **ArUco**：立方體頂面貼約 40 mm 的標記，腕部相機近拍（0.3 m）得到真值。只當參考答案，不參與感知。
- **定位治具**：桌面標格點，把立方體放在已知位置與角度，比對感知結果。

量出位置與 yaw 的 σ、與可見比例的關係，回填上表。

### 模擬要跟著做的事

- 評估模式要 render **RGB + 深度**。
- 模擬的深度與 RGB 太乾淨：加深度飛點、深度雜訊（D435 在 0.65 m 約 2–3 mm RMS）、RGB 曝光變化。
- `near` 改成 0.28 m（§3）。

## 5. Observation

所有位置用**與世界對齊、原點在估計立方體中心的座標系**（只平移、不旋轉）。

不用「立方體座標系」的原因：立方體 yaw 90° 對稱，座標系方向要用 [−π/4, π/4) 的標準 yaw 定義；44.9° 和 −45.1° 是同一個物理姿態，但標準座標系差 90°，而 `cos4θ, sin4θ` 對兩者給出一樣的值，policy 分不出是哪個座標系。手臂的可達性與手腕方向是跟世界綁在一起的，所以這個歧義會直接變成錯誤的夾取。

### Actor（實機拿得到）

| 欄位 | 維度 | 說明 |
|---|---|---|
| 立方體估計 `(x, y)` | 2 | 基座座標系；決定可達性 |
| 立方體 `(cos4θ, sin4θ)` | 2 | 世界座標下，連續、對稱也正確 |
| 立方體可見比例、擬合殘差 | 2 | 估計的可信度 |
| 圓柱 4 × `(dx, dy, 存在)` | 12 | 相對於立方體中心、世界方向，依距離排序 |
| `attempt_idx` | 1 | 0, 1, 2 |
| 上次的 action | 4 | 第一次填 0 |
| 上次的結果（one-hot） | 6 | 無 / 規劃失敗 / IK 失敗 / 下降檢查不通過 / 夾空 / 碰到圓柱 |
| **合計** | **29** | |

拿掉的欄位與原因：

- `q`、`tool_pose`、`gripper`、`holding`：每次做決策時手臂都在 HOME、夾爪張開、沒拿東西（成功就結束了），**永遠是同一個值**。
- 立方體 z：放在桌上時是常數；被推歪由擬合殘差反映。

**`holding` 仍然需要**，但用在成功判定與上次結果的「夾空」，不在 obs 裡：用夾爪角度判斷（夾住 45 mm 方塊停在 +0.506 rad、命令 +0.800；夾空閉到底），實機的 2F-85 也回報位置。

### Critic（asymmetric actor-critic，只在模擬）

actor 的 29 維，加上立方體真值 `(x, y, cos4θ, sin4θ)` 與圓柱真值 4 × `(dx, dy, 存在)`，共 45 維。

### 備案

圓柱依距離排序時，兩根距離相近會互換順序，obs 會跳動。訓練不順的話改成**立方體周圍的 2D 佔據格**（例如 24 × 24、每格 10 mm），從感知輸出的圓柱清單畫出來，訓練不用 render、實機拿得到，而且與順序無關。

## 6. RL 介面

### 一步 = 一次夾取嘗試

```
MoveTo(預抓取點 = 夾取位姿 + descend_m)    cuRobo，繞開圓柱
[檢查直線下降無碰撞]                        §2
MoveZ(-descend_m)                           IK 直線下降
Grip(close=True)
MoveZ(+lift_m)                              抬起
```

失敗的話回 HOME、張開夾爪、重新感知。

### Action

`[dx, dy, dz, yaw]`：

| 維度 | 範圍（初值） | 說明 |
|---|---|---|
| dx, dy | ±20 mm | 對估計立方體中心的偏移，世界方向（§5 的座標系）；也用來補償感知誤差 |
| dz | −10 ~ +15 mm | 相對於 `GRASP_Z` |
| yaw | [−π/2, π/2) | **世界座標下的絕對角度**；對齊立方體的面，是從 `cos4θ, sin4θ` 學到的一個對應 |

yaw 與 yaw+π 對手臂不等價，初版先限制在 [−π/2, π/2)，記錄另一半的失敗率，需要再擴。支援 `action_normalized`。

### Episode 與成功判定

- 最多 `max_attempts = 3` 次；成功就結束；立方體被推出可達區域或掉下桌就終止。
- 成功：抬起後立方體 z 比初始高 ≥ `lift_m` 的一半，`Idle(30)` 之後仍然成立（真值判定）。

### Reward（初值）

| 項目 | 值 |
|---|---|
| 成功 | +1.0 |
| 每次嘗試 | −0.05 |
| 規劃失敗 / IK 失敗 / 下降檢查不通過 | −0.1 |
| 手臂或手指碰到圓柱（`ContactSensor`） | −0.3 |
| 立方體被推離 > 30 mm 或掉下桌 | −0.5 |

## 7. 訓練與評估的兩種模式

| | 訓練模式 | 評估模式 |
|---|---|---|
| planner 的世界 | 桌子 + **這個 episode 的圓柱** | 桌子 + **mapper 建出來的地圖** |
| 相機 render | 關 | 開（只有 wrist，RGB + 深度） |
| 開頭掃描 | 不跑，直接放到 HOME | 跑 |
| 立方體與圓柱的觀測 | 真值 **加上誤差模型** 合成 | **感知模組**從掃描算出來 |
| 規模 | 128 環境以上，GPU PhysX（§9） | ≤ 8 環境，每環境一個 planner server |
| 用途 | 大量樣本 | 量真正的成功率；校正誤差模型 |

### 訓練模式：每個環境有自己的世界

每個環境、每個 episode 的圓柱位置都不同，**不能共用同一個世界**（`pick_place` 不建圖時可以共用，是因為世界是靜態的）。三種做法：

| 做法 | 內容 | 規模上限 |
|---|---|---|
| A. 每環境一個 server | reset 時送 `set_world` | 受 RAM 限制，約 8–12 個 |
| B. 共用 server、每次規劃前換世界 | server 保存每個環境的圓柱，規劃前 `update_obstacle_pose` | 可以很多環境，但規劃是循序的 |
| C. `BatchMotionPlanner` | cuRobo 0.8 的批次規劃（`multi_env=True`），每環境一個碰撞世界，一次規劃所有環境 | GPU 記憶體；128 環境以上唯一可行的做法 |

**固定尺寸的圓柱讓 B 和 C 都便宜**：世界範本是「桌子 + 4 根圓柱」，建一次；每個 episode 只更新位姿，不存在的用 `enable_obstacle(False)` 關掉。

先做 B（驗證訓練流程），再做 C（用 GPU 必需）。兩者都實作成 `lab/planner_pool.py` 裡的 `PlannerPool`，上層不用改。

server 的 `set_world` 類指令只在 `--no-mapping` 的 server 上允許；開了 mapping 的 server 收到要拒絕（和 `a66bc0a` 同一個精神）。

### 評估模式的地圖

只有 wrist，地圖完全由掃描與之後的移動建出來。`pick_place` 的經驗是 wrist 單獨的覆蓋範圍很有限（量過整個 cycle 只涵蓋 x 0.30–0.45、y −0.45–+0.30），所以**掃描姿態要專門設計成涵蓋工作區**，並用 `WatchBox` 對每根圓柱量體素數，確認掃描完每根都在地圖裡、而且整根柱身都有（不只頂面）。

### 訓練與評估的差距要量

訓練時 planner 知道準確的圓柱，評估時只有地圖。這個差距是 M6 的主要數字。

## 9. GPU vs CPU：幾個環境 GPU 才會比較快

### 現有量測（`docs/isaaclab.md`，不建圖、一個 seed = 一次 pick + 一次 place）

| 環境數 | CPU | GPU（cuda:0） |
|---|---|---|
| 1 | 0.8–1.4 s | — |
| 8 | 3.5–5.2 s | 19–21 s |
| 32 | 7–8 s | 22–23 s |

GPU PhysX 每一步約 12 ms（1 環境）到 20 ms（8 或 32 環境），**幾乎不隨環境數增加**；CPU PhysX 1 環境每步 0.8 ms。

從 8 到 32 環境，**CPU 和 GPU 每多一個環境都多約 0.13 s/seed，斜率幾乎一樣**。這段增加的不是物理引擎，而是兩邊共有的成本：每環境的 Python 迴圈（`for e in env_ids`）和規劃請求（2 個 server 循序處理 32 個規劃）。

### 推估的交叉點：約 100–150 個環境（未量測）

GPU 每步約 20 ms 固定，CPU PhysX 的純物理成本大約每環境 0.1–0.2 ms/步（從 32 環境時 CPU 仍快 3 倍反推），兩者相等大約在 **100–150 個環境**。這是外插，**要量**，而且前提是：

1. **Python 的每環境迴圈要先向量化。** 否則 128 環境時共同成本（約 0.13 s/seed/環境 × 128 ≈ 17 s）比物理還大，看不出差別。
2. **規劃要批次化**（§7 的做法 C）。這個情境本來就需要每環境一個世界。

### 讓 GPU 更早贏的槓桿

- **Solver iterations**：現在是 64/16，GPU 的固定成本大致跟迭代數成正比。降到 32/8 可能讓交叉點大幅提前，但 2F-85 的四連桿與夾持力要重新驗證。
- **訓練模式不 render、不掃描**，GPU 上之前遇到的相機 Fabric 問題不相關。
- `replicate_physics=True` 在大量環境時減少複製時間。

### 不管 PhysX 在哪，GPU 都一直在用

cuRobo 規劃、`BatchMotionPlanner`、RL 網路訓練本來就在 GPU 上。PhysX 放 CPU 或 GPU 是獨立的選擇，`--device` 切換，兩種都保留。

### GPU 記憶體（RTX 5080，16 GB）要量

GPU PhysX（128–256 個 UR5 + 2F-85，預估 1 GB 以內）、`BatchMotionPlanner`（批次 128–256，未知，可能是大宗）、RL 網路（很小）。

### 結論

- **目標**：訓練模式用 GPU PhysX + `BatchMotionPlanner`，128–256 個環境。
- **驗收**：M5 的基準測試，環境數 {32, 64, 128, 256} × {cpu, cuda:0} × solver iterations {64/16, 32/8}，量每秒夾取嘗試數與 GPU 記憶體。量出來 GPU 沒贏就用 CPU，不硬用。

## 10. 吞吐量（粗估，待 M5 量測修正）

| 模式 | 規模 | 每秒夾取嘗試 |
|---|---|---|
| 訓練，做法 B | 32 環境，CPU | 數次（規劃是瓶頸） |
| 訓練，做法 C + GPU PhysX | 128–256 環境 | 目標數十次 |
| 評估：建圖 + 掃描 | 4 環境，TiledCamera | < 0.5（掃描佔大宗） |

評估的掃描每個 episode 都要跑，比 `pick_place` 的重掃更長（多了斜視姿態與每姿態多幀平均）。評估每次幾百個 episode，幾個小時。只有 wrist 一台相機，每環境的 render 成本比原本兩台低。

## 11. 風險與待量測

- **HOME 的可達性與視野**：相機在 0.65 m 高往下看，UR5 帶著整串腕部配件要到得了，手臂本身不能擋住視野。
- **掃描姿態的安全性**（§3）：評估模式下掃描時 planner 還不知道圓柱，姿態與姿態之間的移動必須對任何配置都安全。
- **wrist 單獨建圖的覆蓋**：`pick_place` 量過覆蓋很有限；掃描要專門設計，並用 `WatchBox` 確認每根圓柱整根都在地圖裡。
- **遮擋**：0.65 m 高時陰影約 0.73 d，要量取樣的拒絕率；太高就調整掃描姿態或提高 HOME。
- **self-mask margin 0.18 m**：wrist 相機一直看得到自己的夾爪；掃描時手臂離圓柱近，圓柱可能被當成手臂遮掉。
- **手腕在圓柱之間**：可行夾取的判斷一定要用 server 的碰撞檢查（完整機器人球體），不能只看手指。
- **模擬深度與 RGB vs 實機 D435i**：量到的感知誤差是下限。
- **`floor_z = 0.02` 與立方體**：要確認 collision-aware IK 不會因為立方體的體素拒絕預抓取點。
- **`BatchMotionPlanner` 不會 retry**，規劃失敗率要重新量；它是私有模組，升級 cuRobo 時可能變動。
- **圓柱 kinematic（撞不倒）**：避免「撞開再夾」；實機上會倒，碰撞懲罰要夠重。

## 13. 還沒決定、需要討論的

1. RL 函式庫與演算法：rsl_rl 已驗證能接；episode 很短（1–3 步），PPO 的 `gamma` 與 rollout 長度要重新設，也可以考慮 SAC 之類的 off-policy 方法。
2. 要不要固定做近拍（§4），看 M4 的 yaw 精度再決定。
3. 圓柱數量上限與課程的最終難度。
4. 下降段碰撞檢查在評估模式下，要排除估計立方體周圍多大的範圍。
5. 掃描姿態的數量：越多地圖越完整、感知越準，但評估越慢，實機每次夾取前也越久。
